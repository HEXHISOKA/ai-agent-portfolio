# 26. 数据库切换（MySQL 与 SQLite）

这一版把数据库后端做成了**按 URL 自动分支**：`DATABASE_URL` 的 scheme 决定走 MySQL 还是 SQLite，
业务代码、ORM 模型、接口层都不需要改。目的很直接——本地演示继续用已有的 MySQL 数据，
1 核 1G 的服务器上用 SQLite，省掉 MySQL 常驻的 300~450MB 内存。

## 一、怎么切

只改 `backend/.env` 里的两行：

```ini
# SQLite（单机轻量部署）
DATABASE_URL=sqlite:///./data/ecom.db
QUERY_DATABASE_URL=sqlite:///./data/ecom.db

# MySQL（本地演示 / 已有数据库）
# DATABASE_URL=mysql+pymysql://root:mysql@127.0.0.1:3306/ecom-analysis-agent
# QUERY_DATABASE_URL=mysql+pymysql://ecom_ro:***@127.0.0.1:3306/ecom-analysis-agent
```

改完必须重启后端，`settings` 是导入时实例化的。

## 二、把 MySQL 数据搬到 SQLite

```bash
cd backend

# 1) 试运行：只统计行数，不写盘
./.venv/Scripts/python.exe -m scripts.migrate_to_sqlite

# 2) 真正执行（目标文件存在时要加 --replace，会先删掉旧文件）
./.venv/Scripts/python.exe -m scripts.migrate_to_sqlite --yes --replace
```

脚本会按外键顺序写入（users → products → orders → reviews → 报告/预警 → agent_runs/steps/feedbacks），
并做两层对账：**每张表行数** 与 **`products.price` / `orders.amount` 的合计**。
两者都 OK 才算迁移成功，有差异会返回退出码 3。

也可以指定其他源和目录：

```bash
./.venv/Scripts/python.exe -m scripts.migrate_to_sqlite \
  --source "mysql+pymysql://root:mysql@10.0.0.5:3306/ecom-analysis-agent?charset=utf8mb4" \
  --target "sqlite:////opt/ecom/data/ecom.db" --yes
```

## 三、代码里动了什么

| 文件 | 改动 |
|---|---|
| `app/database.py` | 按 scheme 分流；SQLite 下建库目录、启动时设一次 WAL、每个连接设 `busy_timeout` / `foreign_keys` / `synchronous`；查询引擎用 `mode=ro` 打开同一个文件 |
| `app/services/nl2sql_service.py` | 提示词里写真实后端（`SQLite 3` / `MySQL 8`）；sqlglot 的 `read` / `dialect` 跟随后端；`MAX_EXECUTION_TIME` 只对 MySQL 加；错误码判定分方言；金额列补回两位小数 |
| `app/agent/nodes.py` | 解析 SQL 的 `read=` 跟随后端，不再写死 mysql |
| `scripts/migrate_to_sqlite.py` | 新增，负责迁移与对账 |

`SQL_DIALECT` 常量从 `app/database.py` 导出，其他地方一律引用它，不要再出现字面量 `"mysql"`。

## 四、SQLite 下三件必须知道的事

**1. 只读查询靠文件层，不靠账号**

MySQL 那边是 `ecom_ro` 只读账号；SQLite 没有账号，改成用 `file:...?mode=ro&uri=true` 打开查询引擎，
再叠一层 `PRAGMA query_only=ON`。实测写入会直接报 `attempt to write a readonly database`，
比权限表更硬。注意顺序：**必须先让库进入 WAL，再建立只读连接**，
否则运行中切换 WAL 时并发写会随机报同一条只读错误。

**2. 金额会从 Decimal 退化成 int/float**

SQLite 没有 decimal 类型，`text()` 原生查询直接返回 `299`(int) 或 `7170.8`(float)，
而 MySQL 返回 `Decimal('299.00')`。处理办法是在 `execute_select` 里按查询树找出
来源是 `price` / `amount` 的输出列（含 `SUM(amount) AS amt` 这种别名），统一 `quantize` 成两位小数。
实测覆盖：明细列、聚合别名、中文别名、无别名 `SUM(amount)`、`quantity*price AS 小计`。

⚠️ 业务页面（`/api/ecommerce/*`）走 ORM，MySQL 和 SQLite 返回的都是 Decimal，
再经 FastAPI 序列化成 `399.0` 这样的浮点，两边表现一致，不需要额外处理。

**3. 执行超时保护消失**

`/*+ MAX_EXECUTION_TIME(5000) */` 是 MySQL 优化器提示，SQLite 会当成注释忽略。
现在靠 `LIMIT` 最大 200 行 + `busy_timeout` 控制风险；如果以后数据量上来，
需要给查询连接加 `set_progress_handler` 自行中断。

## 五、并发边界

实测（`journal_mode=WAL` + `busy_timeout=15000`）：

- 8 线程各写 10 条：三轮全过，单轮约 0.05s
- 2 写 + 4 读混合：写全部成功，读零错误
- 单进程 uvicorn 下，一次问答会写 10 条左右的 `agent_run_steps`，无压力

但 SQLite 是**单写者**。以下情况应该换回 MySQL：

- 起多个 uvicorn worker（`--workers 4`）
- 把 webhook 接收和定时任务拆成独立进程，与 API 同时写

## 六、回滚

把 `.env` 两行换回 mysql 即可，SQLite 文件留着不影响。
`data/ecom.db` 是单个文件，备份就是复制它（连同 `-wal` / `-shm` 一起，或者在停机时复制）。
